# 首轮验证 PRD（范围讨论中）

## 用途与依据

承接[产品简报](../../briefs/brief-mg_ground-2026-09-18/brief.md)，通过逐问引导定义第一轮教学与闯关验证的范围、行为和验收依据。本文件尚未完成，不作为开发任务或技术选型依据。

当前讨论聚焦产品实现模式、MVP 能力边界、验证方式与分阶段交付安排。用户明确要求暂不展开具体乐理体系、教案或题目内容；只有影响产品范围的内容规模在本阶段讨论，其余在课程与关卡制作时按需细化。保持一次聚焦一个规划问题，不将内容制作决策作为继续产品规划的前置条件。

## 推进顺序与当前状态

按项目 workflow，以决策依赖安排推进：先明确首轮验证目标、成功依据和产品形态，形成 MVP 范围草案；在体验设计中比较操作、场景与视觉方案，必要时针对会改变方案选择的技术疑问做有限验证；再收敛 MVP 与关键体验，进行正式架构选型、规格与任务拆解，随后实现完整可玩流程。PRD、UX 与技术可行性可以相互校准，不能把阶段机械理解为全文定稿后才允许考虑下一阶段。

用户预期大部分开发任务由 AI 承担，明确不需要将个人每周投入时间作为当前关注点或规划前置条件。当前按阶段成果与验证结果组织工作；实际技术依赖、素材需求和维护复杂度在比较具体方案时评估，不据此默认资源无限或已确定交付周期。

核心操作已确定为点选目标、角色自动靠近、到达后直接操作音乐材料或机关；由角色与场景呈现结果。玩家无需持续操纵角色移动。用户当前选择横屏、平面与真实 3D 混合的呈现方式，以课程主线串联独立小场景。平面承载知识介绍和简单玩法，较复杂关卡可由 3D 承接；3D 部分沿用固定镜头。具体镜头构图及切换方式在 UX 中细化，框架和引擎尚未选定。

## CEO / CTO 视角的推进建议

本节为助手对推进方式的建议，具体范围与方案尚需逐项讨论，不视为用户已选择某种玩法、视觉形式或技术栈。用户已调整其中的人力时间假设，按 AI 承担大部分开发、阶段成果驱动的方式继续规划。

### 首先验证的三件事

1. **体验是否成立：** 用户是否愿意完成一个教学与闯关流程，音乐操作及结果是否提供期待的反馈。
2. **学习是否发生：** 从已懂内容验证流程，再用未掌握内容检验理解与独立运用；具体课程目标在内容制作时细化。
3. **后续内容是否能持续制作：** 用第二个单元观察交互与素材复用、内容校验及修改成本，再决定是否需要更多生产工具。

### 决策依赖与阶段产物

| 阶段 | 需要先解决的决策 | 推进依据及对应流程 |
| --- | --- | --- |
| 1. 验证目标与产品形态 | 首轮验证什么、什么结果值得继续；核心玩法、学习与游戏的关系、内容校验责任 | 在简报与 PRD 中记录；已有用户和产品定位沿用，不重做脑暴，不要求先提供个人工时 |
| 2. MVP 范围草案 | 教学与闯关的最小完整体验、能力范围、非目标、成功依据 | `bmad-prd`；音名与唱名作为首个体验载体，暂不编教案与题库 |
| 3. 核心体验与可行性 | 玩家主要操作什么；角色和场景关系；横竖屏；2D/2.5D/3D 表现；触控与鼠标输入；关键反馈 | `bmad-ux` 用草图或画稿比较方案，形成 `DESIGN.md` 与 `EXPERIENCE.md`；根据真实约束进行技术预研，结果回写范围与体验 |
| 4. 范围和方案收敛 | 所选体验是否支持验证目标，技术与素材是否可行，哪些功能保留或延后 | PRD 与 UX 同步收敛，解决会改变主要实现复杂度的决策，不要求先完成所有课程和美术资产 |
| 5. 架构与执行规格 | 运行及渲染方式、音频与交互、内容和关卡规则的边界、进度存储、最小部署、必要测试 | `bmad-architecture` + `codebase-design`，再由 `bmad-spec` 固化；保持最小可用结构，不预设大型后端或关卡编辑器 |
| 6. 首个完整可玩流程 | 一个单元的教案与素材、答案规则、任务拆分和可运行交付 | 每个 epic 的 `SPEC.md`、`stories.yaml` 与关联 Story 是依据；通过 Story Breakdown 和 `bmad-build`，核心业务行为用 `tdd` |
| 7. 验收、试用与扩展 | 真机是否好用、流程是否有价值、陌生知识能否学会、第二个单元能否合理复用 | BMAD 内建审查、`bmad-walkthrough`、最小部署与 `bmad-retrospective`；反馈决定扩课、改玩法或减少投入 |

视觉目标先于最终渲染选型：先明确希望看到怎样的画面、是否需要空间移动与镜头操作，再决定实现是否需要真实三维。技术探针只处理影响决策的具体疑问，需有问题、限额和结论；不是绕过规格直接实现产品。出现可用于讨论的基础画稿后即可重新讨论 Playground，不必等可玩 demo 完成。

用户最初选择真实 3D 加固定镜头，现进一步明确平面介绍及简单玩法与立体关卡结合的方向；[方案比较](addendum.md)保留曾考虑的素材和渲染路线及其成本因素。具体资产制作方式、框架、引擎和渲染配置尚未决定。

### 当前推进重点：Demo 范围与 UX 草图

用户质疑将跨设备进度作为 Demo 阶段的下一项决策。助手撤回该安排：当前需要验证音乐学习与游戏交互能否成立，账号、云同步等完整产品能力不应成为这次体验验证的前置条件；不据此认定用户已经选择本地存档或否定未来同步需求。

下一步由助手基于已有结论整理 Demo 范围草案，再进入 UX 草图与关键状态设计：以音名与唱名为载体，呈现一次引导学习、一次独立操作，以及声音和场景对操作结果的反馈。验证重点是玩家能否理解操作、感受到音乐操作改变场景，并在撤去提示后运用刚学到的内容。该短流程只能提供初步体验与应用证据，不能证明长期学习效果。具体教案仍留到内容制作时细化。

沿用横屏、独立小场景及点选目标后角色自动靠近的方向；呈现方式根据最新偏好调整为平面与 3D 混合，3D 部分使用固定镜头。先通过画稿检查场景、交互区域和反馈，再根据 Demo 的实际需要确定技术方案、规格与实现任务。整个 MVP 的课程范围与后续产品能力保留在本文，但不要求在 Demo 前全部决定。

用户已同意该推进流程。当前 Demo 范围草案如下，待通过 UX 草图检查后收敛；具体机关方案是助手提案，不等同于已批准实施规格。

用户已认可补齐知识介绍后的体验流程方向：进入 → 知识介绍 → 对照示范 → 引导练习 → 独立挑战 → 场景结果。后续已确认教学 UI、场景构图及失败重试/成功通行的反馈结构，详见 [UX 体验记录](../../ux-designs/ux-mg_ground-2026-09-20/EXPERIENCE.md)。这些确认不等同于完整教案、最终资产或学习效果验收。

2026-10-13 用户确认首个 Demo 小范围包含一次 2D → 3D 过渡：完成平面教学和引导练习后，同一组音乐材料及机关进入立体场景完成独立挑战，过渡后镜头固定。此项用于验证已选视觉方向与操作连续性，不扩大为双世界探索、第二套关卡或自由镜头；也不规定后续每节课都要转换维度。具体动效和实现方案通过必要技术预研收敛。

### Demo 范围草案

**要回答的问题：** 在手机横屏的小场景中，学习、直接操作音乐材料和场景结果能否形成易理解且有反馈的循环？撤去引导后，玩家能否初步应用刚学的内容？

**体验边界：** 一个音名与唱名学习单元；一组同类音乐机关，在引导和独立挑战中复用。开场直接进入体验，角色点选目标后自动靠近。引导解释当前操作需要的知识并让玩家试用；挑战撤去逐步提示，改变材料排列或任务实例以避免仅复述点击位置；成功产生可见场景变化和角色行动。具体乐理映射、音符数量与题目在内容制作时确定。

| 能力 | Demo 需要呈现的行为 |
| --- | --- |
| 引导学习 | 明确呈现概念介绍、对照示范和引导练习三个教学环节，再进入独立挑战；介绍需要解释知识是什么与用途，示范连接声音/标记/部件并说明关系，练习允许回看。操作提示不能代替知识介绍；较复杂内容可拆段呈现，不限于机关旁气泡 |
| 音乐交互 | 玩家选择、放置或替换音乐材料，材料本身参与机关运作；具体手势由草图讨论收敛 |
| 独立挑战 | 使用刚学的关系完成新的任务实例；可主动查看提示，使用提示后不计为独立完成 |
| 音视反馈 | 操作引发对应声音、材料状态与机关变化；无声时仍有可理解的结构和状态信息 |
| 单次维度过渡 | 同场景从平面教学进入真实 3D 固定镜头挑战，保持对象可识别和操作逻辑一致；首个 Demo 只验证一次过渡 |
| 错误与重试 | 结果在机关处可辨认，保留操作上下文并允许更换材料再试；具体解释随教案补齐 |
| 完成与复玩 | 机关产生结果，角色自动行动；可重新体验本单元 |

**当前验证不要求：** 账号、跨设备同步、课程目录、长期成长系统、后台内容编辑器、完整 Playground、战斗、EX 关卡或乐队。此边界是 Demo 范围建议，不代表否定未来需求；即便原型需要临时状态，也不在此承诺正式存档策略。

**检查方式：** 草图阶段先检查玩家能否指出目标、操作对象和结果位置；可玩阶段观察首次使用者是否能完成引导、是否理解音乐操作与场景结果的关系、换一个实例后是否能在没有提示时完成。记录卡住的位置、误操作和提示依赖。仅过关、觉得好玩或完成一次不能证明长期掌握；陌生和弦内容与延后复测属于后续学习效果验证。

**交接：** [UX 体验记录](../../ux-designs/ux-mg_ground-2026-09-20/EXPERIENCE.md)保存当前已确认方向、关键画稿入口及单次维度过渡的预研输入；早期线框不覆盖后续确认。PRD 和 UX 均保持草稿，当前没有选定引擎或创建开发任务。

2026-10-13 [首轮技术资料预研](../../research/technical-feasibility-mg_ground-2026-10-13/research.md)已完成，推荐浏览器 Three.js 路线为首个探针候选，非正式选型。下一步以用户主测设备和一屏内的最小样本检验真实 3D、触控与音频；尚无运行性能或学习效果证据。

## 已确认的方向

- 为成年零基础用户提供前后关联的系统乐理学习路线。
- 第一轮以音名、唱名、节拍、大调音阶全半音关系检查流程；之后以和弦命名、组成与色彩检验学习效果。
- 单个小概念的教学约 3–5 分钟，教学与少量闯关合计约 10 分钟，目标为初步理解与应用。
- 主线为 Learn 与 Test，音乐操作需带来可观察的游戏反馈，过关推进章节。
- 核心操作采用点击目标后角色自动靠近、到达后直接操作音乐机关的方式。操作结果通过声音、机关变化和角色表现反馈；保留角色参与的场景感，不以持续控制角色移动为主要玩法。具体移动、过渡与交互状态在 UX 中细化。
- 当前画面采用平面与真实 3D 混合：平面适合知识介绍，也可承载简单玩法；较复杂关卡可由 3D 承接。3D 部分沿用固定镜头。用户喜欢绘本氛围、翻页感觉和由 2D 进入 3D 世界，但要求弱化实体书与学习软件的印象，让人首先感到在玩。具体过渡和各关卡呈现方式在 UX 中细化；不预定双引擎或技术实现。
- 场景采用独立小场景串联，由系统课程主线组织学习进度。具体教学与挑战如何分布于各场景、场景间如何过渡，在体验设计时细化；当前不要求连续可探索的章节区域。
- 首轮以横屏设计手机体验，平板与 PC 兼容该横向布局方向。具体宽高比适配、触控区域及浏览器中的方向提示在 UX 中细化；本决定不指定浏览器或系统强制锁屏机制。
- 音视同步，不方便听时通过文案和动效继续学习适合视觉表达的内容；听觉专项任务的处理待明确。
- 移动端触控优先、兼容 PC，先用浏览器原型小范围试用。
- Playground 保留方向，待用户看到基础场景 demo 或画稿后再构想其玩法，不阻挡教学与闯关范围讨论。

## 待定义的核心体验与范围

首个展示与验证场景已由用户选定为“音名与唱名”，用作体验载体。具体乐理约定、教学素材和题目答案延后到课程与关卡制作；当前只讨论教学、操作、反馈和通关这些能力如何构成完整体验。

1. 教学与闯关的衔接及机关交互体验；核心操作已确定为点选目标后角色自动靠近，再直接操作音乐机关。
2. 首版教学、互动、音视反馈及进度能力的范围和验证目标。
3. 体验设计需明确独立场景间的过渡、横屏在不同尺寸设备上的布局、平面玩法与固定镜头 3D 的衔接及触控/鼠标操作；方案在后续 UX 产物中细化。
4. 成功、错误、提示、重试、中断及无声使用等体验的范围和原则。
5. 根据上述决策安排画稿、技术方案、任务拆解、可玩实现、内容扩展与验证的顺序。

## 延后讨论

- 课程与关卡制作：唱名体系、具体乐理解释、前置知识编排、教学素材和题目答案；进入对应内容制作时再明确。
- Playground：基础场景 demo 或画稿形成后，与用户共同定义。
- EX 关卡、战斗、乐队等：保留候选，未纳入本轮承诺。
- 框架、引擎、音频方案、部署细节：待范围和关键体验明确后进入技术设计。

具体功能要求、用户旅程、质量要求与成功判据将在讨论中补齐，不预先编造验收指标。
