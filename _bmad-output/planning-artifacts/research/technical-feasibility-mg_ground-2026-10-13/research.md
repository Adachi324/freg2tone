# 首个 Demo 技术可行性预研

## 结论

建议先以 **TypeScript + Three.js + HTML/CSS 教学 UI + Web Audio** 验证首个 Demo，使用 Vite 的官方 vanilla-ts 起步模板。这是基于当前范围的推荐，不是已批准架构，也不是性能测试结论。

本轮完成官方资料核对、路线比较和最小探针定义；没有安装依赖、建立应用、运行 3D 或测量真机性能。输入为[当前 PRD](../../prds/prd-mg_ground-2026-09-18/prd.md)及[UX 体验记录](../../ux-designs/ux-mg_ground-2026-09-20/EXPERIENCE.md)。

最重要的两个风险是：手绘概念图如何成为可重复制作的三维素材，以及目标手机上的触控和声音反馈。换一个引擎不会自动消除它们。AI 承担开发不等于图像已具备几何、贴图、动画与稳定的对象身份。

## 路线比较

以下“适配判断”为本项目推断，不是跑分或通用引擎排名。

| 路线 | 官方能力与限制 | 当前范围下的适配判断 |
| --- | --- | --- |
| Three.js + 网页 UI | WebGLRenderer 使用 WebGL 2；提供正交镜头、射线拾取、卡通材质与 glTF 加载。[渲染](https://threejs.org/docs/pages/WebGLRenderer.html)、[镜头](https://threejs.org/docs/pages/OrthographicCamera.html)、[拾取](https://threejs.org/docs/pages/Raycaster.html) | 推荐先验证。教学文字可沿用网页布局，小场景只需少量机关动作；代价是学习流程、反馈编排与音频管理需要自己组织。 |
| Babylon.js + 网页 UI | 提供场景、动画、拾取、音频、材质编辑工具和 Inspector，支持 WebGL/WebGPU。[功能表](https://www.babylonjs.com/specifications/) | 最接近的备选。如探针发现我们在重复搭建大量场景工具或动作设施，应转而比较它，而非继续扩建自制引擎。当前不需要其完整功能面。 |
| Godot Web 导出 | 单线程 Web 导出是当前默认路线；Web 采用 Compatibility/WebGL 2。Sample 音频模式有功能限制；Stream 模式可用更完整音频功能但延迟更高。[Web 导出](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html) | 可以采用，尤其当原生应用及关卡编辑器成为主要诉求。当前需额外验证 Web 导出、教学 UI 与音频模式的配合，暂不列首选。 |
| Unity Web 导出 | Unity 6.0 文档已列出移动浏览器支持，不能沿用“Unity Web 不支持手机”的旧结论。[兼容性](https://docs.unity3d.com/6000.0/Documentation/Manual/webgl-browsercompatibility.html) | 也可实现。本项目目前未要求复杂角色控制、物理或大型内容制作流程，暂没有证据说明引入完整编辑器/导出链路能带来更大收益。未测其包体或帧率，不声称一定更慢。 |

浏览器优先沿用现有产品决定；将来发布原生手机应用需要单独评估分发、WebView、音频生命周期和平台适配。不能承诺网页代码无需改动就等价于原生应用。

## 最小实现方向（待选）

### 同一套对象，两种视觉状态

建议保持一个学习/挑战状态来源和一套对象标识，2D 与 3D 只改变呈现。平面阶段可以使用同源的扁平贴图/平面几何、正交镜头和弱光照；展开时切换对应几何与预设镜头，结束后固定。**正交镜头本身不等于 2D**，需要实际检查平面阶段的画面语言。

不要求每个物件都连续形变，也不先制造两套独立场景状态。转场必须让材料和目标仍能辨认；若仅靠改变镜头没有明显的入立体感，应调整资产和过渡设计，而不是宣称已达成目标。现有桥、机关与角色的空间关系仅作探针的参考。

### 手绘资产

建议探针只制作一个简化角色、三枚材料、一套槽位机关和一座会运动的桥。地面/机关/桥用真实几何，远景装饰可使用分层插画。可用手绘色彩贴图、受控明暗及轮廓表现；Three.js 的 toon 材质提供相应基础，但不会自动生成现有概念图的画风。[MeshToonMaterial](https://threejs.org/docs/pages/MeshToonMaterial.html)

探针先用简单几何确认空间与手感，再为同一小块场景做风格样本。长期资产可通过 glTF/GLB 进入场景；模型制作工具暂不绑定。[GLTFLoader](https://threejs.org/docs/pages/GLTFLoader.html)

需保留可编辑模型或生成脚本、贴图来源、枢轴与动作信息。此前整张生成图适合作为风格和构图参考，不能直接当成关卡模型，也不应期待另一张生成图可作为严丝合缝的动画帧。

### 教学 UI 与触控

网页层承载正文、按钮、回看和声音开关，3D 画布承载对象与机关；避免把清晰中文说明烘焙到纹理里。首个探针用点选材料后点选槽位，不依赖精确拖拽。

统一 Pointer Events 处理触屏与鼠标，再把坐标转换为场景拾取；教学面板上的事件不得穿透到机关。[Pointer Events](https://developer.mozilla.org/en-US/docs/Web/API/Pointer_events)

小圆片的视觉尺寸不是有效点击尺寸，需要检查扩大的命中区域是否与邻近材料冲突。固定镜头下角色先用预设路径自动靠近；只有未来路线复杂度实际增加时才讨论导航系统。

### 声音与同步

一次明确的用户点击用于创建/恢复 AudioContext；音乐音色与翻页拟音分开控制。浏览器可能阻止自动播放，因此不能一进入页面就假定已经有声音。[Web Audio 最佳实践](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Best_practices)

短音符/和声音响可先用合成或预解码采样，具体音色是待听取的体验选择。探针不需要麦克风、吉他识别或完整编曲设施。若后续出现持续节拍/乐队编排需求，再评估 Tone.js 等音乐调度设施。

音乐事件以音频时钟调度，视觉反馈读取相同事件的时间；不以普通计时器决定音符落点。[start 调度](https://developer.mozilla.org/en-US/docs/Web/API/AudioScheduledSourceNode/start) 必要时利用输出时间戳辅助对齐，但它是估计，不能消除硬件、蓝牙和浏览器延迟。[输出时间戳](https://developer.mozilla.org/en-US/docs/Web/API/AudioContext/getOutputTimestamp)

切到后台时暂停当前尝试中的声音与反馈；回来后检查音频状态，不重播一串积压事件。[页面可见性](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API) 无声模式可以验证操作/结构，不计为听觉能力验证。

### 代码组织与发布范围

预研只提出三个职责集中处：学习/挑战规则、场景呈现、声音播放。规则不读取网格坐标判题，换美术不改变答案；声音与场景都消费同一次规则结果，避免各自重复判定。这是后续架构讨论的输入，不在此建通用插件体系或跨引擎抽象。

首个探针仅需静态网页与本次会话状态；不增加服务器或账号，也不据此确定正式存档策略。选择部署服务和公开发布仍是独立步骤。Vite 官方有 vanilla-ts 模板与静态构建路线，无需为这次探针先引入完整应用框架。[Vite 起步](https://vite.dev/guide/)

## 最小技术探针

建议范围上限是 **一屏、一次转场、一套机关、三枚材料、一段短音频反馈**；不是再做一套完整 Demo。先验证以下四个问题，每个问题只做必要变体，发现问题优先定位资产/交互/浏览器原因，不立即更换全部技术。

| 问题 | 要观察的证据 | 通过/转向条件 |
| --- | --- | --- |
| 真实 3D 与风格连续性 | 展开前/中/后画面，真实遮挡与桥运动，同一对象辨认 | 用户能认出同一组对象并感到进入立体空间；若只像换图片，修改过渡/素材，不能算通过 |
| 触控是否可靠 | 横屏点选、取消、重试、打开/关闭教程的操作记录 | 操作不穿透，无重复提交；误触需复现并调整命中区；PC 鼠标可复用相同规则 |
| 音频是否可靠 | 首次解锁、快速重复操作、后台回来、静音后的行为；扬声器与常用耳机分别测试 | 声音可恢复、无卡音或积压播放；记录体验延迟，不能用代码时间戳冒充声学测量 |
| 设备负担 | 具体机型/系统/浏览器、冷启动可交互时间、资源字节、帧时间分布、重复运行稳定性 | 明确在哪些设备成立；预算和阈值待测试设备确定。桌面窗口缩小不能替代手机验证 |

先取得主测设备信息，再定义性能验收数值。至少区分用户主测手机、平板（如有）与 PC；后续正式支持 iOS 和 Android 前应补另一系统实测。

## 主测设备与待验证条件

2026-10-15 用户确认主测设备为 **iPhone 13 Pro Max**。首轮暂按 Safari 规划（助手默认，尚未由用户确认浏览器）；iOS 和浏览器版本在实际测试时记录，不因此阻塞探针范围整理。平板与 Android 设备尚未指定。

首轮设备验证覆盖横屏布局与安全区、点选命中和面板事件隔离、首次声音解锁、切后台后的恢复，以及 2D→3D 转场和机关动作的稳定性。扬声器先测；常用耳机若参与测试，单独记录。机型信息本身不构成性能或兼容性通过证据。

首条验证路线仍建议 Three.js，这是可回退的候选，不能把设备确认当成最终架构批准。2026-10-15 已按用户同意产出[最小技术样本规格](../../../specs/spec-demo-technical-probe/SPEC.md)，含实现边界和验收条件；采用 Three.js 作为探针工程默认，非最终选型。现已通过一个 Story 在 `app/` 实现样本，规则/构建与桌面浏览器检查通过；[实施验证记录](../../../implementation-artifacts/probe-verification.md)保存审查修复、画面与测试证据。iPhone真机及用户观感仍待验证，未据此批准最终选型。

## 体验回写（2026-10-16）

用户认为整场2D→3D翻转缺少实际用途，并认可始终立体、纸面教学开合的调整。当前样本已按Story 2实施，工程验证见[第二版记录](../../../implementation-artifacts/probe-v2-verification.md)。这表明维度切换不应成为固定流程，并非Three.js路线通过主测真机验收；真实机关互动、声音、手机表现仍需分别验证。
